# ADR-0046：先将立绘及配套能力拆为插件

## 状态与背景

本提案尚未实施，不改变当前产品支持范围。当前先拆出完整立绘链路，后续再讨论 Live2D、3D、音色组合及其
表情/动作协议。实施顺序、代码入口和验收见[角色能力插件化计划](../plans/character-composition.md)。

后端实施前先评审[设置 demo](../../desktop/frontend/prototypes/settings-demo/README.md)，
用原有设置外壳和模拟表现选项确认交互是否易懂。demo 不确定新资源格式或跨形态表情协议，
也不代表本 ADR 已接受或立绘拆分已完成。

现有 Plugin Runtime v4 已提供插件安装、Python 运行环境、Service 与生命周期。角色系统仍把默认立绘、
表情图片和图片选择方法放在公共 Profile 中，提示词直接读取图片标签，桌宠直接创建立绘控制器，工坊和归档
也按固定图片字段工作。仅将控制器移到插件目录，会保留这些耦合。

长期希望同一个角色组合不同表现和音色，当前尚未确定其他形态如何表达和选择表情。先完成已有立绘的拆分，
可以明确现有职责和接口，不必同时发明一套尚无消费者的多模型协议。

## 决策提案

### 立绘能力覆盖运行、编辑与资源交换

将立绘格式解释、图片校验、表情候选与图片映射、渲染、相关设置、工坊编辑和归档类型适配归入同一个插件。
宿主保留角色身份、人设、聊天与历史、播放、窗口、通用路径安全、草稿持久化和发布事务。

公共角色模型只持有资源描述。资源实例 ID、格式 type 与插件 ID 分开，避免同一插件以后只能对应一份资源。
旧格式识别保留在明确的兼容边界；图片业务不继续散落在 Core、通用工坊或通用归档器。
旧包在读取时归一化，不启动即批量搬迁文件，也不激活过去未生效的 renderer 字段。

第一阶段仍使用一套当前立绘。完整包保持兼容往返，并支持单独导出立绘组件、导入另一角色的草稿，
以验证资源、编辑和文件边界已完整拆分。多表现列表和多音色组合留到后续。

### 保留 portrait 协议，迁移候选来源与消费逻辑

立绘插件提供当前资源的表情标签和缺省信息，宿主用它构建现有提示词；插件根据回复的 portrait 与 tone 选图。
普通聊天和主动回复消费同一份绑定快照。人格、语言约束、分段 JSON、TTS 语气和历史归宿主管理。

ChatSegment、Timeline 和公开事件继续保留 portrait。旧字段名称可以留在兼容协议中，
不为去掉名称而更换历史格式，也不把插件扩展为可以任意重写整个系统提示词的框架。
其他形态的持续表情、一次动作和模型参数怎样表达，等需求明确后再演进领域合同。

### 复用 v4，增加受管理的前端入口

插件安装包携带现有 Python 注册/适配部分，以及预构建的渲染模块和工坊编辑模块。
静态 manifest 与 Inventory 描述资源类型、服务及模块入口，未启用时也可诊断缺少什么能力。
现有 presentation 分类字段保持展示用途，不参与资源匹配；不新增另一套插件管理器或通用运行时。

RendererHost 管理挂载、就绪、事件、视口、布局/命中和销毁。现有立绘控制器迁入插件，
保留预加载、过渡和 generation 隔离。公共宿主不按插件 ID 硬编码实现。
预装立绘插件离线可用，但可以按现有规则停用或由兼容插件替代。

原生窗口、拖拽和鼠标穿透机制保留，插件提交经过验证的布局/命中数据。
现有 Rust 图片处理可作为立绘适配使用的宿主工具，不为了目录归属重写成熟平台代码；
公共资源描述不要求任意未来表现都提供图片宽高或 alpha mask。

### 保持数据写入与执行边界

沿用 [ADR-0044](0044-character-studio-same-app-window.md) 的 studio 窗口和 Core 唯一写入者。
插件编辑器读写绑定工作区、资源 ID 和草稿修订的区域，发布、目录替换、取消与恢复由宿主完成。
不能让工坊模块直接写已安装角色包。作者资源、个人显示偏好与运行结果分开，现有语音行为本阶段保持。

代码入口来自用户安装的插件，角色包只提供数据。前端模块按可信插件代码处理；同一 WebView 中的模块
不具备 Python worker 的进程隔离，不能宣称为恶意 JavaScript 沙箱。保留 CSP，限制正常桥接接口，
不执行角色资源中的脚本，不依赖运行时 CDN。实例撤销时同时撤销资源授权、回调、订阅和计时器。

## 备选方案与理由

只迁移渲染控制器改动较少，但 Profile、提示词候选、工坊与归档仍然绑定图片，不能实现完整能力替换。
因此把这些配套责任一起迁移，底层通用文件事务和成熟窗口机制继续复用。

立即设计 Live2D/VRM 并统一 expression/motion，可以较早暴露新模型差异，但当前交互语义尚未确定，
会把立绘拆分变成另一轮多模型设计。本阶段保留现有协议，后续用真实模型检验并修改扩展合同。

让 Python 插件逐帧远程操作 DOM 会增加高频 IPC；另换通用插件框架又会重做已有安装和生命周期。
选择 v4 管理插件、前端模块实际绘制，按已有需求提供小的宿主合同。

将前端编辑器接到角色包的任意脚本入口虽然省事，但混淆数据导入与代码安装，也绕过草稿写入边界。
代码仍通过插件安装，角色资源和草稿通过宿主管理。

## 后果与接受条件

改造跨越角色加载、Assistant 接线、Core/Rust/WebView 表现协议、工坊与归档。
好处是立绘运行与制作由同一能力负责；代价是需要明确的模块生命周期、静态声明和草稿资源接口。
不要求把每段底层图片代码都移出 Rust，但要求公共业务不再直接理解立绘字段或拥有隐藏回退实现。

完成依据是旧包正常运行与编辑、portrait 选图和 TTS 行为保持、插件可停用/替换、工坊草稿可恢复、
立绘组件可跨角色往返，以及受影响平台的真实立绘窗口验收。自动化或替代插件夹具不能证明 Live2D/3D 可用。
缺失插件时保留包和公共编辑入口；未知字段、语音及其他资源不得因普通保存而丢失。

接受本 ADR 时记录实际接口与验证范围，再更新状态。当前不取代已接受的插件内核、原生窗口或工坊决策；
后续新形态若改变这些取舍，另行记录，不将提案当作已经交付的承诺。
