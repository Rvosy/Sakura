# ADR：公开更新资料与私人管理服务分开

## 问题

客户端需要稳定读取更新资料，维护者则需要编辑发布草稿、查询诊断和导出原始报告。若把这些能力混在同一个公开入口，管理服务故障会牵连更新读取，也容易让 CI 获得超出发布资料所需的权限。

## 当前决定

公开版本资料使用静态 JSON；私人控制台管理草稿和发布，诊断接收端负责写入诊断数据库。官网独立构建与发布。反向代理按用途暴露接口，公开 API 不转发管理路由。

服务使用现有 FastAPI、SQLite 和 Nginx 能力。控制台通过认证访问，数据和写入目录按服务职责分开；具体部署值由仓库模板与部署配置维护。

CI 只导入发布草稿，不直接覆盖公开清单。维护者确认后，服务端按发布锁与实际写入结果更新公开文件。官网同步保留服务目录和证书等隐藏入口。

## 理由

读取公开资料不需要依赖完整控制台会话，静态交付适合当前访问方式。私人写入链可以独立处理冲突、权限和失败，诊断查询也不应阻塞客户端本地操作。

CI 生成资产与维护者发布面向用户的资料是不同责任。把交接点放在草稿，能检查平台资产、版本说明和实际下载地址，同时保留人工编辑。

## 影响与代价

需要分别构建和管理官网、控制台与接收端，明确各自健康状态。代码包上传不表示服务已重启，草稿导入也不表示已向用户发布。

同一版本的重复导入和人工修改必须有冲突处理。诊断导出可能含原始用户错误，只能通过受保护的管理入口取得。服务失败不更改本地聊天和配置结果。
