# ADR：Core 与插件采用独立进程

## 问题

模型、语音、记忆和工具插件可能依赖同一 Python 库的不同版本，也可能加载无法及时中断的原生库。一个插件的安装和故障不应迫使用户修改其他插件或重装整个应用。官方功能也需要可以被普通插件替换。

## 当前决定

桌面 Shell 管理 Core 及其后代进程树。每个启用插件使用独立进程和依赖目录，共用基础 CPython 与轻量 SDK；Core 自身只保留宿主所需依赖。

官方与第三方插件走相同的运行和公开服务接口。内置身份决定分发方式，不提供私有运行特权。插件的普通跨进程服务传递 JSON 和受管理的资源描述，不共享 Python 对象或直接导入其他插件源码。

安装器统一使用现有 uv 能力准备私有依赖。共享下载缓存可以减少重复文件，但不会把依赖变成全局可导入包。普通启动读取已经安装的依赖，安装和明确重试才准备依赖。

## 理由

依赖版本冲突需要解释器级隔离，仅改变目录组织不能让同一进程同时导入两个不兼容版本。独立进程也让停止失控任务和隔离原生库故障有明确归属。

通用运行时只理解服务、事件、处理钩子、配置、资源和生命周期，领域能力留给消费者与插件，替换实现不需要修改 Core。钩子通过现有 RPC 返回 JSON 修改结果，按顺序交给下一步；插件继续在独立进程运行。

## 影响与代价

逐插件进程增加内存和序列化成本。插件作者需要处理服务失效，并正确结束自己创建的任务、线程和子进程。长任务与大文件使用既有任务和 Artifact 接口，不能把同步对象调用的假设带过进程边界。

这种隔离不提供恶意代码沙箱：插件仍以当前用户权限访问文件和网络。安装来源由用户选择，前端模块同样属于可信插件代码。

具体契约见[插件运行时](../specs/plugin-runtime.md)、[桌面运行时](../specs/desktop-runtime.md)和[公共 SDK](../development/plugin-sdk.md)。资源失效与恢复策略见[生命周期决策](explicit-lifecycle.md)。
