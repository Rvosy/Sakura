# ADR：由数据和能力的拥有者负责校验

## 问题

同一资源如果在插件、Core、Rust 和前端分别执行完整校验，规则会逐渐冲突。任意数量或名称限制也会让正常角色和配置在导入通过后仍无法使用，内部新增字段则可能被误判为协议破坏。

## 当前决定

外部配置由所属服务解析，插件格式由实际消费它的插件解释。内部调用复用已经解析的结果，各层只处理自身路由、授权、生命周期与所需字段，不复制整套业务校验。

字段的读取和写入范围分别管理。读取允许保留未知扩展，局部写入只执行本次提交的字段；凭据由拥有它的配置服务生成公开投影，前端不靠猜测字段名避免泄漏。

保留实际边界需要的限制：通信帧与内存预算、授权路径、更新签名、进程回收、取消以及真实设备能力。增加限制必须对应明确问题；内容哈希仅沿用外部协议、签名或认证的要求。

## 理由

格式拥有者最清楚数据如何使用。一处解析能让错误更接近来源，也避免调用链每经过一层就增加一个不同门槛。边界授权和任务失效仍有独立价值，不能与重复业务检查混为一谈。

## 影响与代价

消费者需要保留原始错误和必要上下文，不能用通用“校验失败”替换它。可选表现或插件资源错误按所属能力报告，不拖垮无关流程。

测试关注保存后的数据、实际请求、取消、资源保留和授权效果。新增内部字段、普通文案变化或函数重构不应导致无业务含义的失败；已经删除的能力也不需要再用测试证明它不存在。
