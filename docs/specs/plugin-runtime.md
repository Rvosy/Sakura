# 插件运行与生命周期

插件为 Sakura 提供模型、Assistant、语音、记忆、工具和角色表现。运行时负责安装、依赖、进程和服务连接，领域功能由相应插件负责。官方插件与第三方插件使用同一套公开接口。

本文说明插件从安装到退出的约定。具体调用格式见 [Plugin API v4](../development/plugin-sdk.md)，内置插件随应用发行的规则见[发行与存储](release-storage.md)。

## 职责边界

| 参与者 | 负责内容 |
|---|---|
| Shell | 启动 Core、维持单实例、最终回收应用拥有的进程树 |
| Core 插件运行时 | 发现插件、处理硬依赖、启动独立进程、路由服务、撤销失效能力 |
| 插件安装器 | 准备代码和 Python 依赖、发布安装结果、保留失败恢复信息 |
| 插件 | 实现服务和业务、持有自己的连接与后台任务、清理自己创建的资源 |
| 设置界面 | 展示真实安装和运行状态，保存草稿，表达启停、重载和卸载操作 |
| 公共 SDK | 提供配置、服务、事件、资源和宿主能力的统一入口 |

每个启用的插件使用独立进程和独立 Python 依赖环境。依赖冲突与进程故障不应扩散到无关插件。插件仍以当前用户权限访问文件和网络，进程隔离不等于安全沙箱。

通用运行时依据 Manifest 和实际注册能力工作，不以插件 ID 编排模型、记忆或语音业务。领域之间通过公开服务连接，不相互导入私有源码。

## 身份与能力声明

`plugin.yaml` 是安装包入口。`api: 4` 表示 Plugin API 版本；`id` 是稳定插件身份，`entry` 指向入口类。显示名称和分类可以变化，不能用它们替代身份。

| 声明 | 含义 |
|---|---|
| `provides` | 本插件启动后必须发布的 Service key |
| `requires` | 启动及失效传播使用的硬依赖 |
| `enabled` | Manifest 默认值，用户显式启停选择优先 |
| `priority` | 启动排序信息，不能用于暗中解决同名服务冲突 |
| `presentation` | 插件页的分类与图标，不改变权限或依赖 |
| `visuals`、`ttsResources`、`frontendModules` | 对应领域的静态资源声明 |

同一 Service key 同时只能有一个启用提供者。出现冲突时报告冲突对象，不按加载顺序偷偷选择其中一个。兼容性依据 API、服务和资源契约判断，不额外用主程序版本号阻拦可用插件。

## 安装、发现与启用

用户可以从市场、ZIP 或文件夹安装。安装器识别包根目录的 Manifest，先在暂存位置准备代码和依赖，成功后才发布到用户插件目录。失败保留原有安装，不把部分完成状态显示成安装成功。

普通发现只读取应用内置插件和用户已安装插件。`plugins/optional/` 中存在源码不代表已经安装，也不会因普通启动自动启用。新安装插件默认停用，由用户启用并应用设置；更新沿用已有启停选择。

已经外置的 Mem0、手机网页端、SenseVoice、GPT-SoVITS、Genie 和 Spine，升级后只识别用户安装版本。残留在内置目录中的旧副本不参与列表、加载和安装冲突判断，也不在用户版卸载后重新启用。发现过程保留这些文件及用户配置、数据；缺少用户版时可从市场或本地包安装。

启停配置兼容旧字段和重复项，同一 ID 取最后一个有效的布尔值。无效条目不阻断其他插件；启停值无法识别且没有有效选择时保持停用。读取不改写配置，启停和卸载只修改目标插件的条目，保留其他条目与附加字段。

插件目录展示安装事实，运行状态展示当前进程结果。已经下载、安装或准备好资源，不等于插件已启动，更不等于外部服务已经可用。

内置插件不能卸载，可替代的默认能力可以停用。用户插件卸载移除所选副本的代码；还有同 ID 副本时保留共享依赖和启停选择，最后一个副本卸载后才清理依赖。插件私有配置和业务数据始终保留。重新安装相同插件可以继续使用这些数据。

## Python 依赖

依赖声明按 `requirements.lock`、`requirements.txt`、`pyproject.toml` 的顺序选择；项目声明可配 `uv.lock`。安装器复用 uv，为每个插件准备独立环境，不向主 Python 混装插件依赖。

普通启动只使用已经准备好的依赖，不联网补装。缺少依赖时插件报告具体状态，由安装或修复入口处理；无关插件仍可启动。

默认下载源、用户显式 uv/PIP 配置及可用离线依赖由安装器统一处理。插件可以声明版本约束和专用来源，不自行复制通用安装器。默认源的明确资源缺失与用户指定来源分别处理，来源规则见[插件指南](../guide/plugins.md#下载插件资源)。

代码、依赖、模型资源和外部服务是不同对象。插件更新不应删除模型；连接外部服务也不赋予 Sakura 回收该服务进程的责任。

## 启动与就绪

运行时先建立进程通信，再调用 `setup(context)`。插件在 setup 中登记服务、设置、工具和事件，耗时下载或长期工作放到后台，避免堵住状态查询和取消。

| 状态 | 含义 |
|---|---|
| `disabled` | 当前选择不启动该插件 |
| `starting` | 进程与能力仍在准备 |
| `active` | setup 成功，声明的服务已发布 |
| `failed` | 安装、依赖或启动失败，保留具体原因 |

active 只说明插件已提供能力。语音模型下载进度、MCP 连接状态和记忆初始化状态由领域服务另行报告，不能用插件 active 代替这些结果。

硬依赖缺失、服务冲突或进程退出，只影响目标插件和实际依赖它的消费者。可选能力失败不得把整个 Core 标记为不可用。聊天、语音和表现各自发布就绪状态。

## 服务调用与实例身份

`context.provide` 公开服务和明确的导出方法；参数与结果使用 JSON。大内容通过 Artifact 交付，不把 Python 对象、回调、进程句柄或任意文件路径当作跨进程契约。

`context.get` 调用当前可用服务；`context.bind` 固定当前插件服务实例。需要 begin、poll、cancel、release 的任务必须始终使用同一绑定，不能在中途重新查找同名服务。

Core 每次启动有新的 generation，插件每次重载有新的 scope。服务绑定、回调、任务和临时资源都属于取得它们的实例。同一插件 ID 被重新加载，不会让旧任务重新有效。

提供者失效后，旧绑定返回 `SERVICE_BINDING_EXPIRED`。旧结果不能写入新实例，旧 disposer 也不能撤销后来登记的同名能力。运行时不将结果未知的调用自动重放到新进程。

调用没有统一的业务超时。消费者只有在协议或实际任务要求下设置期限；等待超时不能证明远端工作已停止，更不能证明外部操作未执行。

## 处理钩子

插件可在聊天输入、模型请求与响应、工具执行和回复提交处登记处理器。处理器按顺序接收数据副本，通过返回值修改当前步骤或说明中止原因。原始用户输入、角色身份和服务绑定仍由对应模块维护。

钩子与插件实例绑定，显式撤销、停用和重载都会移除登记；已经在途的旧回调结果不再并入处理链。可选处理器失败保留原始错误并继续，声明失败即中止的处理器阻止当前步骤。已经执行的外部动作不会因后置处理失败而回滚。公开用法和扩展点见 [SDK：处理钩子](../development/plugin-sdk.md#处理钩子hooks)。

## 配置保存与运行态应用

包内 `config.json` 提供默认值，用户覆盖保存在插件私有数据目录。局部修改使用合并保存，未提交字段保持原值。升级默认值不覆盖用户显式配置。

插件配置回调接收完整有效配置，并报告 `applied`、`restart_required` 或 `error`。只有实际更新连接、缓存和相关后台状态后才返回 applied。没有热应用处理器时，变化需要局部重载。

保存成功和应用成功分别报告。应用失败保留已保存数据、仍可用的运行状态与原始错误；下一次聊天不代替用户修复。进行中的工作继续使用自身配置快照。

普通字段编辑由设置页统一提交，测试、下载和 Collection 增删按动作立即执行。取消编辑不回滚已经执行的外部动作。详细草稿规则见[设置](settings.md)。

## 停用、重载与升级

停用或重载先阻止旧实例接受新工作，撤销其能力和资源，再结束在途任务与进程。消费者的失效传播沿硬依赖关系进行，不重启无关插件或整个应用。

插件通过 `context.effect` 登记清理，按反向登记顺序执行。显式 disposer 与退出共用清理责任；连接、线程和子进程由创建者停止并回收，不能依赖界面继续轮询才结束。

升级和重新安装保留用户配置、模型、业务数据和启停选择。市场、ZIP 和文件夹更新共用安装流程，先准备候选代码和依赖，再停止目标插件及硬依赖消费者。代码、依赖成对切换；文件切换或提交失败恢复旧版，进程中断留下的事务在发现插件前恢复。插件导入和启动由运行时负责，启动失败保留新版本、启停选择和具体错误，允许继续修配置或重新安装；消费者启动失败不撤销提供者的更新。旧文件清理失败只报告警告，不能将已完成的更新显示为安装失败。

本地包与唯一的已安装用户插件同 ID 时，执行更新或重新安装。同 ID 有多个副本时显示各自的版本和目录，先卸载多余副本。同一插件的安装请求依次执行；准备依赖不占用其他插件的设置保存入口。切换时采用最新的启停选择；准备期间已卸载的目标不再更新。

提交记录写入失败同样执行回滚。恢复失败的安装保留在列表中，再次安装、启停或卸载前先处理旧事务；成功后清除恢复错误，并恢复因提供者缺失而未能启动的消费者。重新安装先准备新包和依赖，再恢复旧事务，不尝试启动即将替换的旧代码。无法解析的事务记录连同备份保留到 `.failed-update-*` 目录，再应用已验证的新包。未完成的事务不能跨过后续更新继续生效。

统一日志记录安装准备、版本切换、文件回退、更新恢复和卸载结果，包含插件身份、相关目录、版本或耗时。失败保留原始原因，安装完成仍提示未启动的插件。启动时记录忽略的旧内置副本及用户版状态，刷新列表不重复记录。

更新提醒和市场展示共用版本筛选规则。只有已安装、可独立更新且存在更高兼容稳定版本的插件进入提醒；撤回版本、预发布、内置插件和身份冲突不进入。提醒成功记录按插件 ID、目标版本和本地日期保存，失败、取消和其他聊天不记为成功。提醒发送前移除已经更新或卸载的候选。

主程序升级保留已安装的可选插件，发行范围见[发行与存储](release-storage.md)。

插件替换仅表示能力替换，不意味着新插件能读取旧插件私有数据库。数据转换必须有明确格式与入口，不通过更改插件 ID、清空目录或重装来掩盖不兼容。

## 错误与诊断

安装、依赖准备、进程启动、setup 和业务任务分开记录阶段与真实结果。清单错误在应用启动时记录，后续扫描保留诊断供界面显示，不随刷新重复写错误日志；依赖下载失败的各次尝试留在调试日志，最终失败统一报告。长步骤先记录开始，失败保留原始异常、子进程输出和受影响对象，见[诊断](diagnostics.md)。

正常取消、重载和 scope 撤销不是业务故障。非关键通知或清理失败不应覆盖原始错误，也不能宣称资源已经释放。Python 负责业务清理，关闭边界统一使用 10 秒协作期限；同批插件共享期限，不逐个累加。Shell 给业务收尾留出 30 秒，35 秒内完成最终进程树回收。

## 关键行为

- 更新一个已停用插件后，它仍停用；原配置、模型和数据可继续使用。
- 某插件依赖安装失败时，其他插件与设置仍可使用，失败对象可以从原入口修复。
- 同名服务被重新加载后，旧任务的 poll、取消和结果提交不会操作新服务。
- 关闭插件设置或切换角色后，迟到结果不能覆盖新的编辑对象。
- 一个服务提供者崩溃时，硬依赖它的消费者明确失效，无关能力保持运行。
- 卸载再安装同一插件，用户数据仍在；更换为另一个插件不会自动混用私有数据。

进程隔离的理由见 [ADR：进程与插件隔离](../adr/process-plugin-isolation.md)，升级原则见 [ADR：保留数据的更新](../adr/data-preserving-updates.md)。相关实现入口为 [`app/plugins/`](../../app/plugins/) 和 [`plugin_runtime_application.py`](../../app/core_host/plugin_runtime_application.py)。

公开用法以 [SDK](../development/plugin-sdk.md) 为准，领域约定分别见[模型](model-services.md)、[聊天](conversation.md)和[工具与 MCP](tools-mcp.md)。
