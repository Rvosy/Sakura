# 官网、更新入口与私人控制台

在线服务提供公开产品资料、更新清单和可选诊断接收；私人控制台供维护者发布资料及分析故障。
桌面启动、聊天与本机设置不依赖控制台在线。在线服务失败不能改变本地操作的实际结果。
部署命令和模板目录约定见[服务运维](../development/services.md)，客户端更新见[发行](../development/release.md)。

## 模块职责

| 模块 | 负责的内容 | 不属于它的职责 |
|---|---|---|
| 官网 | 下载入口、使用说明、产品介绍及开发者入口 | 写诊断数据库或直接发布更新清单 |
| 公开静态服务 | 返回客户端认可的版本、更新、公告和已知问题 JSON | 管理登录、草稿编辑和诊断查询 |
| 诊断接收端 | 接收客户端报告与指标，写入诊断数据库 | 对外提供私人控制台 |
| 私人控制台 | 草稿编辑、人工发布、诊断浏览及导出 | 充当客户端必需的实时服务 |
| CI 草稿导入 | 将已构建发行资料送入私人草稿库 | 自动使新版本对客户端可见 |
| 反向代理 | TLS、入口隔离、控制台认证与路由 | 替代应用保存和发布状态 |

官网、诊断接收和控制台可分别构建、发布和恢复。
Cloudflare Worker/D1 目录是独立示例，不是桌面客户端正在使用的接收实现。

## 公开入口

| 入口 | 契约 |
|---|---|
| api.sakura.cialloo.cn/service/v1/ | 公开静态 JSON，跨来源读取 |
| adm.sakura.cialloo.cn/admin/ | 经认证的私人控制台 |
| telemetry.cialloo.cn | 桌面发送服务配置的诊断地址 |
| sakura.cialloo.cn | 官网及兼容的 service/v1 静态路径 |

API 域名只转发明确列出的诊断 POST 和静态 JSON，不能把管理路由暴露到公开入口。
旧诊断入口若转发到同一接收端，应保持 POST 方法和正文，不靠重定向变成读取请求。
静态入口只提供 releases.json、latest.json、announcements.json 和 known-issues.json。
静态 JSON 使用 UTF-8、正确类型、CORS 和缓存约定，只允许 GET/HEAD。
公告与已知问题清单当前为空数组；这不表示控制台已有对应编辑发布功能。

## 更新资料契约

releases.json 使用 schema 1，描述最新版本、发行地址、发布时间、下载项和更新清单地址。
minimumSupported 为空表示未设置最低版本说明；它不授权客户端强制安装或关闭本地功能。
urgent 表示维护者标记的重要程度，不改变安装需遵守的用户操作约定。
下载项包含 Windows 安装版、Windows 便携版、macOS arm64，可附 Linux x64 AppImage。

latest.json 使用 Tauri 更新清单，包含 version、notes、pub_date 和 platforms。
平台项保留对应产物的原始下载 URL 与更新签名，不能用下载页 URL 代替更新包。
Windows 与 macOS 对应 windows-x86_64 和 darwin-aarch64；便携包使用独立下载项。
发布 Linux 时，普通 AppImage 下载与 AppImage.tar.gz 签名更新包必须成对提供。
安装包继续由 GitHub 分发，静态服务保存发布资料而不复制整套发行产物。
notes 保留该版本的更新说明，不用历史累计日志或 CI 过程输出代替。

## CI 导入与草稿

1. 发行构建生成 schema 1 的 release/updater 资料，并经限定入口送入控制台。
2. 服务端核对公开格式，保存私人草稿，返回可继续编辑的草稿身份。
3. 维护者查看目标版本、下载地址、签名、说明及当前线上版本。
4. 草稿可保存说明、重要程度和最低版本说明，保存不会更新公开文件。
5. 维护者明确发布后，才进入公开资料写入流程。

同一版本的相同 CI 资料重复导入返回原草稿，避免重复任务制造多份待发布内容。
同一版本的资料已经变化时明确失败，不能静默覆盖维护者已经检查或编辑的内容。
CI 身份只可导入资料，不直接写公开目录，也不获得通用 shell。
草稿按 ready、publishing、published、failed、interrupted 或 discarded 区分状态。
已发布草稿不能直接继续编辑；需要修改时重新导入并按新的发布操作处理。

## 保存、发布与冲突

保存携带用户所编辑的原草稿内容，服务端发现内容已变化时拒绝覆盖并保留原数据。
发布同时检查草稿内容和用户核对过的线上版本，防止旧页面覆盖新的线上状态。
冲突后保留草稿和具体原因，维护者刷新核对后可以再次发布，不自动代替用户合并。
保存与发布共用发布锁，静态文件采用原子替换，不暴露只写了一半的 JSON。
版本降级被拒绝；改变代码部署版本不等于可以把客户端最新版本倒退。

服务端确认资料写入并保存发布状态后，控制台才显示已发布。
发布失败记录失败状态和原因，不能因请求已发出就给成功提示。
服务进程中断留下的发布任务应呈现可检查、可重试的状态，不假定上次已经成功。
公开清单更新、GitHub 发行产物存在、官网部署完成是不同事实，应分别检查。

## 诊断接收契约

接收进程提供 v1 兼容入口、v2 操作与模型指标，以及 v3 原始错误报告。
v3/errors 接收单次报告，正文最多 128 KiB，并按 reportId 去重。
v2 事件每批最多 10 条、整个请求正文最多 8 KiB；模型指标每批最多 10 条、整个请求正文最多 16 KiB。
格式与体积要求属于公开服务边界，不在客户端业务调用处重复实现一套校验。
接收进程健康检查包含数据库可用性，进程端口打开不代表已经能够保存记录。
原始错误、身份关联、隐私范围与终态定义见[诊断规范](diagnostics.md)。

数据库保存收到的事实，不根据没有报告推断某次客户端操作成功。
原始记录最多保留 90 天；旧 received_at 按北京时间解释，导出明确时区。
真实报告、运行事件和模型指标通过安装、运行、后台代次及操作关联。
测试数据使用隔离数据库或显式测试标记，不能把测试样本混入生产统计。

## 私人控制台与分析包

控制台通过反向代理认证，应用继续核对允许的 Host；写请求要求同源 JSON。
诊断详情保留原始文本和完整报告，展示时不执行报错内容中的 HTML。
筛选可以限定时间、构建、版本、安装、运行、后台代次、操作、分类和平台。
分页和导出沿用相同筛选范围，不能界面显示一个范围却导出全部数据。
仅有 operationId 时不能跨所有运行猜测时间线，必须有明确运行范围。

分析包包含筛选条件、实际数量、原始报告、关联记录与质量说明。
默认排除明确标记的测试数据，维护者可以显式包含它们。
导出独立于发布锁；生成超过 5 分钟或 1 GiB 时明确失败，不提供部分 ZIP。
临时下载保留一小时，完成与过期状态均由服务端结果确定。
源码映射按 buildId 关联，缺失时保留未知位置，不使用其他构建猜测。

## 数据权限与部署职责

接收端写诊断数据库；控制台只读诊断库，并写自己的草稿、发布操作及导出数据。
公开 JSON 由受控发布流程写入，CI 上传身份与官网同步身份不直接代替控制台发布。
数据库、导出、发布锁和公开文件位于持久目录，不能随服务代码版本目录清理。
代码回退保留期间产生的数据，数据库兼容需独立处理，不能直接覆盖旧快照。

仓库提供控制台 systemd、Nginx、证书续期和 CI 导入模板。
模板中的路径和账号按目标环境配置，部署结果通过实际接口检查。
接收端的代码目录、运行账号和进程管理方式由对应部署环境配置。
官网同步保留 service/ 和站点隐藏文件，避免覆盖更新资料、证书入口或服务数据。

## 关键业务场景

| 场景 | 应有结果 |
|---|---|
| CI 成功导入发行资料 | 私人草稿可见，公开版本暂不改变 |
| 两个页面先后编辑同一草稿 | 旧页面保存冲突，保留已保存内容 |
| 页面停留期间线上已发布新版本 | 发布被拒绝，要求刷新核对 |
| 诊断接收失败或控制台离线 | 本机聊天照常，客户端按诊断规则处理待发错误 |
| 官网发布 | 只更新站点内容，更新 JSON 与服务数据保留 |
| 分析包生成失败 | 显示真实失败，没有可误认完整结果的部分下载 |

入口和权限分离的取舍见[公开服务与私人管理](../adr/public-private-services.md)。
