# 日志、原始错误与诊断报告

诊断应让维护者看出用户正在做什么、停在哪一步、失败的原始原因是什么。
诊断结果服务于排查，不替代业务结果，也不因采集或发送失败阻断原来的操作。
用户查阅方式见[故障排查](../guide/diagnostics.md)，代码接入见[诊断开发](../development/diagnostics.md)。

## 职责与数据边界

| 内容 | 负责者 | 保存目的 |
|---|---|---|
| 普通运行日志 | Rust 统一日志服务 | 本机操作步骤、状态和故障定位 |
| 插件日志 | 插件通过宿主日志服务提交 | 保留插件身份，复用同一写入和轮转链路 |
| 原始异常诊断 | 捕获错误的业务边界 | 保留消息、原因链、栈和恢复错误 |
| Agent Trace | 默认 Assistant | 解释一次操作实际发给模型的内容及模型返回 |
| 远程错误与指标 | Rust 诊断发送服务 | 跨版本、系统和操作关联定位问题 |
| 接收与分析 | 诊断服务、私人控制台 | 原始记录入库、筛选、关联和导出 |

Core 与插件不各自开一套运行日志文件。Python 日志桥、WebView 和 Rust 最终进入统一服务。
插件身份决定写入插件日志还是宿主日志，但两者共用顺序、格式及轮转规则。
日志窗口读取同一服务的快照，窗口显示不形成独立的业务状态或错误数据库。
插件 stdout/stderr 属于进程诊断，不能替代明确的业务日志，也不据此猜测任务已经成功。

## 按用户操作记录步骤

一次操作应串起关键步骤，例如下载安装、解压、运行检查、应用资源和最终完成。
长步骤开始即留下记录，完成时写实际结果；有已知总量时再报告数量或进度。
阶段、对象、必要耗时和退出码帮助定位，不要求每层函数都打印进入与退出。
同一操作沿用操作编号，模型调用可继续关联调用序号，不能为每一层制造新身份。

info 记录开始、实际变化、就绪和有产出的完成。
warning 记录可恢复故障及清理问题；error 记录请求或初始化失败。
正常取消、插件重载、未启用的可选能力不作为故障。
轮询成功、心跳和无变化的内部同步进入调试级别或不记录。
同一错误由能说明业务后果的边界报告，不在每层转发时重复打印。

下载完成只说明下载完成，模型加载完成只说明可以推理。
播放结束、插件安装完成、公开清单发布等必须由对应真实结果确认。
恢复操作失败应附加为第二个错误，不能覆盖最初造成故障的原因。

## 原始错误贯穿整条链路

错误码用于分类，原始文本、异常链、栈和失败步骤用于定位，两者都保留。
在实际捕获点提取异常，不等到跨线程或跨进程后再生成无关调用栈。
Python 异常、WebView Error、原生错误和提供方错误通过现有诊断载体传递。
业务界面可以给出简短摘要，但错误详情必须仍能看到与复制原始原因。
前端显示原始文本时按文本处理，不能把报错中的 HTML 当成可执行界面。
通用错误码不足以判断权限、余额、模型或设备故障时，不自动猜测具体原因。

路径、Unicode、模型名、请求地址、HTTP 状态与子进程输出可以是必要证据。
边界替换已知凭据以及明确的认证信息，不把所有路径或异常文本一概抹除。
不要主动加入聊天正文、Prompt、记忆、工具输入输出、完整配置、环境变量或请求体。
原始异常可能包含失败数据片段，因此不能把原始错误描述成绝不含用户内容。
格式和体积预算由统一边界管理，调用点不自行截短到只剩通用提示。

## 本机文件与非关键失败

普通日志位于用户目录的 data/logs，宿主与插件使用各自的统一文件。
运行与插件日志约 10 MiB 轮转，各保留 5 份旧文件。
日志服务提交成功只说明接收了记录，不保证此刻已经写入磁盘。
日志队列、桥接或磁盘失败不会令聊天、保存或关闭失败，也不触发业务重试。
出现日志写入故障时保留可用的诊断提示，不能递归记录同一故障或另建零散 writer。

## Agent Trace

Agent Trace 记录实际模型请求与回复，包括系统提示、历史、上下文、记忆及工具正文。
它按一次操作组织，并区分该操作内的模型调用及用途，使并发操作不会混成一段。
Trace 中保留消息来源，能区分用户消息、历史、程序注入观察与工具结果。
结束时记录实际成功、失败或中断状态，不因已有部分输出而宣告整轮成功。

Trace 使用独立文件 sakura-agent-trace.log，按完整操作成块提交。
单文件约 32 MiB 轮转，总量最多约 512 MiB，并清理超过 30 天的旧文件。
图片等二进制输入记录格式和大小摘要，不保存 Base64 图片正文。
凭据继续清洗，但对话与记忆正文仍是私密数据，分享 Trace 前需要由用户检查。
Trace 不随普通诊断自动上传；Trace 写入失败也不阻止聊天收尾。

## 关联身份

| 标识 | 解释范围 |
|---|---|
| installationId | 本机随机诊断身份，可由用户重新生成，不绑定账号或硬件 |
| runId | 一次桌面运行，区分重启前后 |
| generationId | 一个后台运行代次，区分 Core 重启或替换 |
| operationId | 一次用户或插件业务操作，串联请求、阶段与结果 |
| reportId | 一份错误报告，用于重传去重 |
| buildId | 对应构建产物及其源码映射，不能由相似版本代替 |

操作编号本身不足以跨运行唯一定位；控制台时间线应结合运行和安装身份查询。
缺少关联事件意味着证据不完整，不能据此推断任务成功或用户没有遇到故障。
映射文件缺失时保留未知源码位置，不套用另一构建的 source map。

## 远程报告与指标

远程诊断复用同一错误捕获链，由 Rust 统一发送，不由各插件直接另建上传器。
v3/errors 保留原始错误证据；v2/events 保存结构化操作结果；v2/model-calls 保存模型调用指标。
HTTP 状态成功不能取代报告入库成功，客户端根据实际接收结果处理待发记录。
错误报告按 reportId 去重，不因网络重试产生多份同一报告。
服务商返回的 Token 用量与本地估计分开，不能用估计冒充实际消耗。
正常取消单独计为取消，未收到终态不计为成功。

诊断开关同时控制统计和错误发送，关闭后不影响本地功能。
可持久暂存的是待发错误报告；普通统计和模型指标不落盘补传。
网络失败保留有效待发错误供后续启动或空闲发送；成功接收后删除本机副本。
关闭诊断或重新生成身份会清理本机旧待发报告，不能继续以旧身份发送。
默认状态、待发容量和保存期限在[统计与隐私](../guide/privacy.md)维护。

## 接收端与私人分析

接收端保存收到的原始报告和关联记录，私人控制台负责筛选、聚合与分析包。
公开接收入口不暴露控制台查询、导出或发布能力。
控制台详情保留完整原始报告，复制结果与收到的 JSON 一致，不只复制摘要卡片。
分页、时间范围、构建和身份筛选必须同时作用于列表、统计与导出。
导出说明实际筛选范围、记录数量及缺失关联，失败时不能交付看似完整的部分包。
服务协议字段见[服务端模型](../../services/sakura/v3_models.py)和[在线服务规格](services.md#诊断接收契约)，运维见[服务指南](../development/services.md)。

## 关键业务场景

| 场景 | 应有结果 |
|---|---|
| 下载成功但解压失败 | 下载步骤完成，整体失败指向解压与原始原因 |
| 提供方异常跨进程回到界面 | 原消息、异常链与栈可查，不只剩请求失败 |
| 错误含密钥和本机路径 | 替换密钥，保留可定位的路径及错误上下文 |
| 用户取消语音或聊天 | 记录取消，失败率不因此上升 |
| 日志磁盘不可写 | 原业务继续，诊断说明写入失败，不重复执行原操作 |
| 上传超时后再次发送 | 复用报告身份，服务端保留一次原始报告 |
| 只有操作编号的时间线链接 | 要求明确运行范围，不把不同运行混在一起 |

诊断边界的取舍见[保留原始错误](../adr/original-diagnostics.md)。
