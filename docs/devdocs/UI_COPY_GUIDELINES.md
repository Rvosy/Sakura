# 界面文案规范

界面只写用户完成操作需要知道的内容。默认不加辅助说明，先删除重复和无用文字，再考虑改写。
这套规则适用于新增和修改的按钮、字段、空状态、通知、确认框、错误及插件贡献的界面文字。

## 先判断这句话是否需要存在

标签、按钮或当前页面已表达的信息，不再写一遍。不要解释显而易见的操作，也不要把实现进度、内部机制和
维护者的判断塞进界面。删掉一句话后，如果用户仍能判断操作对象、结果和后果，就删掉它。

| 避免 | 使用 |
|---|---|
| 添加到角色列表——当前只是本地保存 | 添加到角色列表 |
| 发布后才会出现在角色列表 | 删除；按钮已表达结果 |
| 标题“导入角色”，下方“导入 .char 角色包” | 只保留标题，文件选择器限制格式 |
| 暂无聊天记录，和角色聊几句，记录会显示在这里 | 暂无聊天记录 |
| 长期记忆当前不可用；普通聊天仍可继续 | 长期记忆不可用；有具体原因才显示正文 |
| 主题操作，下面列出配色按钮 | 删除标题，保留按钮 |
| 主动发言冷却；两次主动搭话的最短间隔 | 最短搭话间隔 |
| 设置窗口已连接；暂无可用设置 | 暂无可用设置 |

不要为了让界面显得完整而填满 `description`。没有必要的信息时，省略字段或传空字符串；宿主隐藏空描述，
不保留空行或无效的无障碍引用。对话入口可以亲切，错误和确认框仍应直接表达事实。

参数含义等补充解释放在标签旁的小 `?` 中，不加圆圈、边框或底色，不另占一行。悬停、键盘聚焦或
点击问号可查看说明；离开后收起，点击打开的说明可再次点击、点击外部或按 Esc 关闭。
桌宠、设置和角色工坊的悬停说明共用主题浮层，背景、文字和边框随当前主题变化，不使用浏览器原生
`title` 提示。没有补充信息的控件不加问号；下文列出的操作后果、隐私范围、错误和必要状态仍直接显示。

## 保留影响决定的信息

简短不能以隐瞒后果为代价。下列信息放在相关操作附近，不能因精简而删除：

- 不可恢复的删除、覆盖范围及实际恢复方式。
- 更改目录是否会移动现有文件。
- 草稿已保存、设置已应用和等待重启之间的区别。
- 留空保留原 API Key、清除凭据等会影响保存结果的规则。
- 截图、录音或其他数据实际发送给谁、发送范围是什么。
- 错误的具体原因，以及有证据支持的处理办法。

插件设置弹窗的“完成”只接受本次编辑，外层“应用”才保存，因此“应用设置后生效”仍应保留。
不能把尚未应用的修改描述为“已生效”，也不能在没有恢复机制时承诺“可撤销”。

## 名称和动作保持一致

| 场景 | 用语 |
|---|---|
| Provider 配置页、导航和引导 | 模型服务 |
| API endpoint 字段 | API 地址；外部资料中的 Base URL 可在帮助文档中对照 |
| 凭据字段 | API Key |
| 从服务读取模型目录 | 获取模型列表 |
| 模型列表引用的移除 | 移除 |
| 新角色进入可选角色目录 | 添加到角色列表 |
| 已在角色列表中的角色修改 | 保存 |
| 与角色的对话内容 | 聊天记录 |
| 程序诊断信息 | 运行日志 |

按钮用具体动作或结果。关闭设置和退出应用使用各自的语境：“关闭前保存设置？”与“退出前保存设置？”，
关闭设置时使用“继续编辑”“不保存并关闭”“保存并关闭”；退出应用时使用“继续编辑”“直接退出”
“保存并退出”。“直接退出”放弃未保存修改，确认框标题仍需明确询问是否保存。

不要给每个术语附加中英文括注。API Key、模型名称、文件扩展名和错误码等需要外部核对的内容可以保留。
代码字段和协议 ID 不随界面名称重命名。修改名称时，检查导航、页面、原生菜单、后端返回的提示和用户文档。

## 状态和错误必须有依据

状态来自实际数据，不能凭一个空列表推断全局情况：

- `starting`、`waiting`、`stopping` 分别显示“正在启动”“等待启动”“正在停止”；启用不等于运行正常。
- 日志筛选为空只说明当前筛选没有记录，不能宣布“本次运行没有问题”。读取失败单独显示错误。
- 连接测试成功指出实际测试的模型；获取到模型目录不等于目录中每个模型都可调用。
- 首次配置可能缺少角色或模型，不掌握具体缺失项时使用“请完成首次设置”，沿用现有设置入口。
- 401 可提示检查 API Key；403 只说明服务拒绝访问，不能直接断言余额不足或密钥过期。

错误先给简短、准确的提示。HTTP 状态、已清洗的服务端说明和稳定错误码保留在可展开详情或诊断页中。
不能为了缩短文字丢失排查依据，也不能回显密钥、完整响应或未清洗的私密数据。
外部文本按纯文本渲染，不作为 HTML。只有真实可执行且适用于该错误的操作，才提供重试或修复入口。

普通成功反馈只报结果。开关已经显示状态时，不再弹出同义通知；系统自动改变状态时可以提示原因。
删减可见文字时保留控件标签、对象名称和必要的读屏反馈，图标按钮仍需可理解的无障碍名称。

## 开发与审查

每次新增或修改界面，提交前检查以下事项：

1. 删除所有只复述标题、控件或显然操作的说明；不要用更长的句子替换它们。
2. 对照真实调用链，确认名称、作用范围、成功状态和失败原因准确。
3. 保留会影响操作决定的后果；把只供排查的信息放进详情。
4. 同步同一流程的动态提示、后端返回文字、用户文档及相关 Spec。
5. 检查窄窗口、长模型名称、空描述、错误详情和读屏标签。状态判断改变时复用或补充行为回归测试；
   不新增仅比对整段文案的测试。视觉检查与自动测试分别报告。

具体功能行为仍由对应 Spec 定义，本规范不新增保存、重试或恢复机制。首次落实本规范时，按用户要求保留
现有 TTS 专属文案与行为；不以术语统一为由批量重写语音设置、语音包和语音日志。
