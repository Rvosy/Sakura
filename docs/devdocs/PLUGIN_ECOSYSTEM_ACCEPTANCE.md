# 开放插件生态初版验收

日常验收使用已有角色包、模型配置和默认 Assistant，检查插件自己的“对话规则”上下文设置及可选“便签记忆”。
`f9fde091` 引入的主设置“互动方式”已撤回。旧 `chat_executor` 字段直接忽略，无需手工删除；
“专注陪伴”保留为开发样例，暂不能从聊天框选择。安装或启用它也不会切换聊天实现。

M5 已用 TTS Hub 和便签记忆验证公共能力：普通插件可显式绑定服务进程，TTS Hub 据此隔离重载前后的任务；
便签记忆用自己的存储、Collection、Context 和只读工具提供另一种记忆方式。本轮 ASR 实例绑定与便签显式查询修正已完成，
不恢复主设置选择器，不实施 M3/M4 的模型或默认对话拆分。

## 使用已有角色包和配置

先从托盘菜单退出正在运行的 Sakura，再运行仓库中的
[`scripts/start-existing-data.bat`](../../scripts/start-existing-data.bat)。
Windows 默认使用 `%LOCALAPPDATA%\Sakura Development`，这是仓库开发版的日常数据目录。
原来的角色选择、角色包、模型配置、插件开关和聊天记录都从这个目录读取；启动器不创建验收角色，也不重写这些配置。

如果平时使用的是安装版，Windows 安装版的数据位于其程序目录，可明确传入那个已有目录：

```powershell
scripts\start-existing-data.ps1 -UserRoot 'D:\Sakura'
```

启动器只为本次进程指定数据目录。聊天和用户主动保存的设置会直接写入所选目录，它们就是日常使用的数据。
当前正常聊天始终使用默认 Assistant；已有有效模型配置可以继续使用，缺少模型配置时仍需完成配置。

## 默认对话与插件上下文

先发一条普通消息，确认当前角色、模型对话和既有表现正常。主设置中应没有“互动方式”、执行器选择或预设的 Agent 模式。

在插件管理中查看“对话规则”。尚未安装时，可按[插件 README](../../plugins/optional/context_rules/README.md)打包并安装。
打开插件自己的设置，查看“上下文”字段。验收不会自动改写这段文字：已有内容、已有空白和新安装时的默认文本均按原值保留。
需要使用它时由用户启用插件，再发送一条适合当前上下文的问题，检查默认对话是否采用所填内容。

上下文可以同时包含要求与资料，不需要选择用途分类。模型输出有波动时，结合本次请求的 Trace 检查实际内容；
不要仅凭某一句回复断言插件没有生效。停用再启用插件后，设置文本应保持原值，其他插件和角色选择不应变化。

清空、改写文本或旧版配置合并的回归在隔离环境中完成，不为验收覆盖日常使用的内容。
“专注陪伴”不消费 Context，计时结果不能用来判断“对话规则”是否生效。

## 便签记忆的日常验收

使用上面的已有数据启动器，由用户安装 `dist/fact_memory-0.1.1.sakplugin.zip` 并启用“便签记忆”。
也可从 `plugins/optional/fact_memory` 文件夹安装，打包命令见[插件 README](../../plugins/optional/fact_memory/README.md)。
验证时保留原来的模型、角色和其他插件配置。若需要单独比较记忆来源，由用户决定是否暂时停用 Mem0；
便签记忆不会读写或转换 Mem0 数据库。

1. 打开“便签记忆”的插件设置，新增内容“验收项目交付时间是周五下午三点”，关键词“验收项目”，点击“创建”。
2. 发送“验收项目什么时候交付？”。在当轮 Prompt Trace 中检查 `fact_memory` 的 Context 是否带入这条便签，
   再观察回复。模型也可以通过只读 `fact_memory_search` 查询，不能要求每次一定调用工具。
   显式工具查询还应覆盖正文中的“交付时间”：即使它未列入关键词，也能找到这条便签。
3. 把便签改为“验收项目交付时间是周六下午三点”，点击“更新”，退出并重新启动。
   插件列表应保留修改，再次提问的当轮 Context 应使用周六。
4. 删除测试便签后再提问，确认它不再出现在该插件的 Context 或搜索结果中。需要检查停用时，可先重新创建
   这条测试便签，再停用插件，确认当轮不再有它的贡献；重新启用后保存的数据仍在。

Collection 的创建、更新和删除直接持久化，不依赖主设置的“应用”。测试只改用户明确创建的验收便签；
不要清空日常内容。内容最多 1000 字符，关键词可选、最多 200 字符；一次最多召回 5 条，正文合计不超过 2000 字符。
自动 Context 在没有关键词时使用轻量文字匹配；显式工具始终按正文或关键词做字面子串查询，
完整规则见[便签记忆规范](../specs/runtime-v2/fact-memory.md)。已安装 `0.1.0` 时，在插件详情点击“卸载插件”并确认“卸载”，
现有入口会保留私有数据；再安装新版 ZIP、重新启用并应用设置。原启用状态不会保留，数据库、便签及条目 ID 应保持原值。

删除和停用只撤回本插件的后续贡献，已经写进聊天历史或被其他记忆插件保存的文字仍可能影响模型。
因此“回复还提到周五”不能单独证明删除无效；以当轮来源为 `fact_memory` 的 Context 和工具查询为依据。
有多个角色时，可以由用户切换后查看列表，确认角色之间不共享便签，再切回原角色。

自动链路入口为 `tests/integration/test_fact_memory_core_protocol.py`，使用隔离数据、真实 Core/插件进程及受控模型端点。
自动结果与已有数据中的原生窗口和真实模型体验分别记录。

用户已在已有数据环境中试用便签记忆，本地 Prompt Trace 和工具调用记录确认插件在正常 Assistant 中生效。
试用发现的显式搜索漏查正文问题由 `0.1.1` 修正，仓库仅记录问题与验证结论，不复制私密便签或聊天原文。
修正另经 15 项便签聚焦与真实 Core IPC 测试验证，提交为 `4bd53bc5`，新版 ZIP 已生成。
其中卸载重装链路确认重新安装后默认停用、启用后读取原条目 ID 与正文，重启后仍可按正文查询。
自动回归不代替用户安装新版后的日常试用。

## TTS 任务的实例绑定回归

TTS Hub 在任务受理前通过 `context.bind(serviceKey)` 固定 Provider 进程，就绪查询、受理、任务查询和取消共用该代理。
Provider 崩溃后由用户重载同 ID 插件，新任务使用新绑定。旧任务的查询或取消必须报告绑定失效，
不能因为新进程重用了 `jobId` 就作用到新任务；迟到返回也要通过实例检查。

故障注入使用隔离测试及事件/屏障，不在用户日常进程中制造崩溃。普通语音试用只检查当前配置仍能合成和播放，
不能用一次播放成功代替重载竞态验证。接口和错误码见 [SDK](SAKURA_PLUGIN_SDK.md#固定一次操作的服务实例)
与 [Runtime Spec](../specs/runtime-v2/sakura-plugin-runtime-v4.md#51-显式绑定插件进程)。

## ASR 任务的实例绑定回归

语音输入继续使用现有麦克风入口和插件设置。Core 在准备录音时固定 Hub，Hub 在受理识别前通过
`context.bind(serviceKey)` 固定 Provider；任务后续调用不重新查找同名新进程。成功结果进入待回填状态前，
以及首次向 UI 交付文本前，均核对 Hub 和 Provider 实例。绑定失效报告 `ASR_PROVIDER_UNAVAILABLE`，已取消任务保持取消。

隔离测试用真实插件进程及事件/屏障安排重载，覆盖 Provider 或 Hub 在查询、取消、返回期间被替换，
以及成功暂存后首次 UI poll 前的实例更换。确认旧 `jobId` 不会被发给新进程、旧文本不回填，
同时检查录音撤销及读取租约回收。
不在日常数据或用户正在录音的进程中注入故障，不新增自动重绑或重放。

正式语音输入的回归入口为 `journey-asr`，具体范围见 [ASR 规范](../specs/runtime-v2/asr-voice-input.md)。
本轮新增 `tests/unit/test_asr_service_binding.py` 的 6 个真实进程回归均先失败、修复后通过，分别覆盖
旧 `poll/cancel` 在 scope 检查后误发新进程、成功返回时来源失效，以及成功暂存到首次交付之间的来源失效。
最终 `journey-asr` 通过 3/3：Python 45 项、Rust 11 项和前端 22 项通过；Rust 的 1 项真实麦克风测试保持 ignored。
本轮未使用真实麦克风或真实识别模型，也未重新进行原生窗口人工验收；这些体验与绑定竞态回归分别记录。

## 新建隔离验收环境

隔离环境供开发与自动回归使用。在 Windows 仓库根目录运行：

```powershell
runtime\python.exe scripts\prepare_plugin_acceptance.py
```

脚本默认创建 `temp/plugin-acceptance-日期时间-随机标识`。也可以用 `--user-root` 指定新目录；目录已存在时拒绝写入。
它安装“对话规则”并保持停用，只启用内置“立绘”，创建“Sakura 验收”角色和空 Timeline。
环境没有 API 配置，不预选执行器，也不安装计时样例。

脚本通过真实插件进程检查立绘加载；默认 Assistant 应返回 `setup_required/PROVIDER_SETUP_REQUIRED`。
这证明无模型时仍遵循默认聊天的配置要求，不表示聊天已经就绪。检查结束后关闭进程。
`acceptance-environment.json` 记录本次准备结果；未操作原生窗口时，`guiVerified` 保持 `false`。

需要手动查看这套空白环境时，先退出其他 Sakura 实例，再双击生成目录中的 `启动验收.bat`，
或用 PowerShell 运行同目录的 `启动验收.ps1`。启动器只对本次进程设置 `SAKURA_RUNTIME_USER_ROOT`，工作目录使用仓库根目录。
在其中体验模型对话，需要自行配置可用模型。

启动器使用 `desktop/src-tauri/target/debug/sakura.exe`。可执行文件缺失或需要更新时，在仓库根目录编译：

```powershell
cargo build --manifest-path desktop/src-tauri/Cargo.toml --locked
```

准备脚本和启动器不会自动编译。空白角色使用 Sakura 图标作为立绘；它只是检查资源加载的材料。
日常视觉、音频和聊天体验使用上面的已有数据入口验证，结果与自动测试分别记录。

## 执行服务开发回归

[专注陪伴样例](../../plugins/optional/focus_companion/README.md)和隔离测试继续验证真实计时、进度、取消、线程退出、
同操作重复受理、同服务重载及结果提交保护。这些检查由开发消费者显式绑定执行服务，不通过主设置、隐藏配置或插件开关接管聊天。
进度不写助手历史，最终结果只取得一次提交资格；停止未确认时保留占用，不能伪称任务已经退出。

`f9fde091` 的设置切换、无模型计时聊天和 Edge 设置页联接结果属于历史实现证据，不能作为当前产品入口的验收结果。
保留底层合同并不预定最终界面，也不自动启动默认模型或对话能力的进一步拆分。
